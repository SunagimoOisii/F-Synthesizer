# アーキテクチャ診断

このファイルは、既存の開発方針とアーキテクチャを前提にせず、継続開発性の観点から監査する正本です。
`docs/Architecture.md` は現在の構造、`docs/PRODUCT_POLICY.md` はプロダクト判断、`AGENTS.md` は作業ルールを扱います。

## 判断軸

最優先は、個人開発と AI 支援開発を数か月後も安全に続けられることです。
音の気持ちよさ、初心者向け導線、短い編集から試聴までの流れは重要ですが、保守不能な構造を正当化する絶対条件にはしません。

## 現状診断

- 単一 Visual Studio C++ アプリとして、GUI、App、Core、SynthEngine、Config、MIDI、IO に分けている点は個人開発に合っている。
- `gui -> app -> core -> SynthEngine` の依存方向は妥当で、GUI が直接レンダリング実装を持たない方針も維持する価値がある。
- 一方で、機能追加が `include/SynthEngine/SynthEngine.h`、`include/gui/GUIState.h`、config load/save/schema、GUI `.inl` 群に集中しやすい。
- 設定、GUI、プリセット、レンダラを同時に触る変更が増えるほど、AI が正しい追加先を選びにくくなる。
- ドキュメントを少なく保つ方針は妥当だが、方針そのものの見直し先がなかったため、古い判断が暗黙の前提になりやすかった。

## 方針監査

維持すべき方針:

- 個人開発の速度を重視し、過剰なプロセスや大規模テスト基盤を増やさない。
- GUI、App、Core、SynthEngine、Config、MIDI、IO の責務境界を守る。
- 音の気持ちよさ、初心者向け導線、短い試聴サイクルを主要価値として扱う。
- 共通 source capability と schema 判断は `SourceRegistry` に集約する。
- 履歴ログや長い判断ログを増やさず、正本ドキュメントだけを短く更新する。

修正すべき方針:

- 「既存パターン優先」は維持するが、巨大型や巨大ファイルへ追記し続ける理由にしない。
- 「小さく変更する」は維持するが、公開型や保存形式へ影響する変更では実装前に設計確認を行う。
- 「音と UX 優先」は維持するが、保守コスト、検証負荷、AI が迷う変更範囲も機能判断に含める。
- `SynthEngine.h` と `GUIState` は便利な集約点ではなく、肥大化を監視する公開境界として扱う。

削るべき方針:

- 機能を増やすたびに GUI 状態、config、renderer、preset を同時に直足しする進め方。
- 使う可能性があるだけの高度な DAW 機能、プラグイン、共同編集、プロ向け深い操作。
- 正本以外のステータスログ、プロンプト保管庫、ロードマップ履歴。

未決の判断:

- `SynthEngine.h` の source config 群を、将来どの単位で分割するか。
- `GUIState` を永続状態、画面一時状態、非同期実行状態へ分けるか。
- GUI `.inl` 群を、機能単位の `.cpp` へ移すか、現状の include 分割を維持するか。
- config schema、load/save、GUI editor の契約をどこまで自動検証するか。

## 転換案

現状維持強化:

- AGENTS と既存 docs のルールだけを強化する。
- 速度は最も出るが、巨大型と変更集中のリスクは残る。
- 短期の小修正には向くが、数か月単位の拡張には弱い。

段階的整理:

- 既存動作を保ちながら、公開型、GUI 状態、config 契約、renderer 境界を順に小さくする。
- 速度と保守性のバランスがよく、個人開発でも実行しやすい。
- 大きな再設計へ進む場合の準備にもなる。

大きな再設計:

- source config、GUI state、project model、render model を改めて切り直す。
- 長期の保守性は上げられるが、音と GUI の現行体験を壊すリスクが高い。
- 実施するなら、先に現在の主要導線とプリセット音の受け入れ基準を固定する。

推奨:

- すぐに全面再設計へ入らず、段階的整理で境界を固める。
- ただし、大規模再設計を選べるように、公開型と GUI 状態への直足しを抑え、変更理由を残す。
- 大きな機能追加では、実装前に責務、公開型、保存形式、検証範囲を短く確認する。

## 今後の設計レビュー基準

- 変更先の責務が `GUI / App / Core / SynthEngine / Config / MIDI / IO` のどこかを明確にする。
- `SynthEngine.h`、`GUIState`、config schema、preset、GUI `.inl` 群へ同時に触る場合は大きめの変更として扱う。
- 新しい状態や設定を足す前に、既存型への直足しでよいか、別モデルや helper に分けるべきかを確認する。
- GUI は編集と表示を担当し、音作りの実装や config 契約の重複定義を持たない。
- Renderer は実行時の音生成に集中し、UI 都合や保存形式都合を直接持ち込まない。
- ドキュメント更新は、方針変更ならこのファイル、構造変更なら `Architecture.md`、プロダクト判断なら `PRODUCT_POLICY.md`、検証や運用なら `OPERATIONS.md` に置く。
