# プロダクト方針

## 方針

- 最優先価値: 継続開発性。個人開発と AI 支援開発で、安全に機能追加を続けられること。
- 主要価値: 気持ちよい音。
- 主な利用者: 開発者本人と完全初心者。
- トーン: 遊び心があり、レトロゲーム風で、すぐ触って試せること。
- UX 優先順位: 短い編集→試聴サイクル。
- リポジトリ方針: public だが、個人開発の継続性を優先する。

気持ちよい音、初心者向け導線、短い編集→試聴サイクルは主要価値です。
ただし、保守不能な構造や検証不能な変更を正当化する条件にはしません。

## MVP 体験

初心者が、合成理論を先に学ばなくても FM、waveform、noise、レトロゲーム風サウンドに触れられること。

優先するもの:

- 説明よりも直接聴けること
- 精密なプロ向け操作よりも失敗しにくい操作
- 網羅的なパラメータ面よりも、すぐ使える preset
- DAW 的な深さよりも、コンパクトな作業導線

## 対象外

- 高度な DAW 機能。
- プロ専用の深いパラメータ編集を主導線にすること。
- プラグインホスト。
- 共同編集。
- 個人開発の反復を遅くする大規模なテスト・ドキュメントシステム。

## 機能判断ルール

1. 継続開発性を落とさず、音の気持ちよさ、または編集→試聴時間の短縮に効く変更を優先する。
2. 初心者が読めるラベルと導線を優先する。
3. 保守コスト、状態追加、保存形式への影響、テスト負荷、AI が迷う変更範囲を見積もる。
4. 共通 engine behavior は source ごとに重複実装せず、一度だけ追加する。
5. source 固有 behavior は、その音源方式に本当に必要な場合だけ残す。
6. 複雑な機能は、基本の音作りループと責務境界が良くなってから扱う。

## 成功の兆候

- 起動から最初の preview までが短い。
- 1 セッションで何度も編集→試聴したくなる。
- preset から認識しやすいレトロゲーム風の音へすぐ届く。
- JSON 編集なしでも、GUI から有用な音の変化に触れられる。
