# COMMENT_GUIDELINE

最終更新: 2026-02-24 (rev3)
適用範囲: `src/` + `include/`

## 1. 目的

本規約の目的は以下です。

- 可読性を上げる
- 設計理由・背景をコード上で追跡可能にする

## 2. 基本方針

- コメント量は「中程度」を基準とする
- 原則日本語で記述する
  - 識別子・API名・型名は英語のままでよい
- 見出しコメント（セクションコメント）を許可する
- すべての関数に一律でコメントを付けない
- 自明な処理の言い換えコメントは避け、高リスク箇所へ集中させる

## 3. 必須コメント

以下にはコメントを必須とする。

1. 複雑な条件分岐
2. クラス/構造体の役割（概要）
3. ファイル全体の方針・責務（概要）
4. 最適化コード
5. システム内での位置づけが読み取りにくい処理
6. 並行性や所有境界の前提がある処理
7. 公開I/Fで誤用時の挙動差が大きい関数

### 3.3 呼び出し経路・責務境界コメント

ローカルな処理意図だけでは判断が難しい場合、次を1行で補う。

1. 呼び出し経路（どこから呼ばれ、どこへ渡るか）
2. 責務境界（どの層で何を担当するか）

推奨例:

```cpp
// 呼び出し経路: GUI/Config -> Voice初期化 -> Renderer内Stepで適用
// 責務境界: app層で入力整形、SynthEngine層で音生成を担当
```

### 3.4 並行性・所有境界コメント

次のいずれかに該当する場合、前提を明示する。

1. スレッドセーフではない状態更新
2. 再入不可（reentrantでない）な処理
3. 呼び出し主体が限定される状態（例: audio threadのみ）

推奨記述:

```cpp
// 前提: audio thread からのみ呼ぶ。複数スレッド共有は想定しない。
// 所有境界: Voice単位の状態を呼び出し側が一貫して保持する。
```

### 3.5 公開関数コメント（関数レベル契約）

`include/` の公開関数、または外部モジュールから利用される関数のうち、
次の条件に該当するものにコメントを付ける（全関数一律は不要）。

1. 誤用時に音/状態破綻を招く
2. 似た関数と使い分けが必要
3. 並行性・所有境界の前提がある

コメント対象になった関数は、少なくとも次のうち2項目を示す。

1. 目的（いつ使うか）
2. 入力前提（有効範囲、単位、許容値）
3. 副作用（内部状態更新、永続化、I/O）
4. 似た関数との使い分け

特に `Reset` / `SetTarget` のように誤用しやすいAPI対は、
使い分けコメントを必須とする。

### 3.6 高リスク関数の必須コメント

次の関数は、関数先頭または宣言部で意図コメントを必須とする。

1. 状態を破壊的に更新する関数
2. 時間依存・サンプル依存の関数
3. 境界値の丸め/フォールバックを行う関数
4. 失敗時の挙動を握りつぶす関数

### 3.7 コメントを省略してよい関数

次に該当する関数は、名前/型から意図が明確ならコメント省略を許可する。

1. 単純な setter/getter
2. 単純な値変換で副作用がない関数
3. 既存の上位コメント（ファイル/型/ブロック）で文脈が十分に説明済みの関数

### 3.1 クラス/構造体コメントの粒度基準

クラス/構造体の定義コメントは、以下の基準で運用する。

1. 必須
- 役割が名前だけで自明でない型
- 境界型（設定/状態/I/O結果/永続化/診断）
- variantや複数責務の分岐点になる型
- 重要な前提（有効範囲、整合条件、寿命、互換制約）がある型

2. 任意
- 小さなPODで、フィールド名から用途がほぼ明確な型
- 同一ファイル内の局所利用で、呼び出し関係が短い型

3. 不要
- 一時的な補助型で、意図が実装から即読できるもの
- 外部仕様の単純写像で、重複説明が保守コストになるもの（例外規定に従う）

### 3.2 クラス/構造体コメントに書く内容

原則として、型定義の直前に 2-4 行程度で記述する。

1. 何を表す型か
2. どこで使う型か（境界/層）
3. 重要な前提・制約（ある場合のみ）

推奨テンプレート:

```cpp
// <型の役割>
// <主な利用箇所・層>
// <前提・制約・トレードオフ（必要時のみ）>
struct ExampleType
{
    ...
};
```

## 4. 最適化コメントの必須要素

最適化コードには、次を必ず記載する。

1. 目的（何を改善したいか）
2. 前提条件（この実装が成立する条件）
3. トレードオフ（可読性/保守性/制約など）

## 5. 禁止事項

以下のコメントは禁止。

1. ポエム的なコメント
2. `TODO` / `FIXME`（改善・拡張は md ドキュメントで管理）

## 6. 記述スタイル

- 行数上限は設けない（目的達成を優先）
- ただし冗長化は避け、必要情報を優先する
- コメントは「何をしているか」より「なぜそうするか」を優先する

### 6.1 用語の明確性ルール（レビューで機械的に判定する）

「一般性が低い語」「意味が曖昧な語」という主観表現を避けるため、以下のチェックで判定する。

1. 単語置換チェック（Pass/Fail）
- 次の語を使う場合は、同じ行に具体語を併記するか、平易語へ置換すること。
- 対象語: `導線`, `写像`, `昇格`, `温存`, `主キー`, `走査`, `境界`（文脈なし）, `正規化`（内容不明）, `クランプ`（範囲不明）
- 例: `クランプ` を使うなら `0.0..1.0 に丸める` のように範囲を併記する。

2. 外来語チェック（Pass/Fail）
- 英語API名を除き、カタカナ/英語の専門語は日本語で置換可能なら置換する。
- 例: `callback` -> `コールバック`, `wide API` -> `ワイド文字API`

3. 3秒ルール（Pass/Fail）
- 初見レビュアが3秒以内に意図を言い換えられない文は修正する。
- 修正方法は `抽象語を減らす` または `対象/条件/結果を1行追記` のどちらか。

4. 1行具体化ルール（Pass/Warn）
- 抽象語を使う場合、次のいずれかを同一コメントブロック内に含める。
- `対象`（何に対して）, `条件`（いつ）, `結果`（どうなる）
- いずれも無い場合は Warn、誤解が出る場合は Fail。

### 6.2 推奨言い換え表

- `ディスク走査` -> `ファイル一覧を読み直す`
- `導線` -> `操作の流れ`
- `写像` -> `変換`
- `昇格` -> `切り替える` / `有効化する`
- `温存` -> `保持`
- `主キー` -> `基準`
- `正規化` -> `必要な形式にそろえる`
- `クランプ` -> `範囲内に丸める`
- `同一文脈` -> `同一スレッド/同一所有者/同一呼び出し系列`

### 6.3 関数コメントの最小テンプレート

公開I/Fまたは高リスク関数では、次の最小テンプレートを推奨する。

```cpp
// 目的: <この関数を使う場面>
// 前提: <入力制約・呼び出し文脈>
// 副作用: <更新される状態やI/O>
```

### 6.4 Good/Bad 例

Bad:

```cpp
// 同一文脈で管理する
```

Good:

```cpp
// 前提: audio thread からのみ呼ぶ。UI thread との共有はしない。
// 所有境界: Voice単位の current/target は呼び出し側が保持する。
```

### 6.5 空行ルール（可読性）

コメントのまとまりを視覚的に分離するため、次を推奨する。

1. 2行以上のコメントブロックの前後は、原則1行空ける
2. 関数宣言コメントは、コメント直下に対象宣言を置く（間に空行を入れない）
3. 連続する短い1行コメントを多用せず、関連する内容は1つのブロックにまとめる

例:

```cpp
// 使い分け: Reset は即時一致、SetTarget は段階追従。
// 前提: audio thread の更新系列で呼ぶ。
void SetSmoothedTarget(SmoothedParam& param, double target);
```

## 7. レビュー運用

- 規約違反は修正必須
- コメント不足/過剰はレビューで具体的に指摘し、意図を揃える
- 公開関数は「いつ使うか/何を壊すか/何と使い分けるか」が読めることを確認する
- 並行性前提がある箇所は「どのスレッドで安全か」を確認する
- 自明な関数に説明過多のコメントが付いていれば削除を検討する

## 8. 例外規定

以下の場合に限り、規約の一部を例外適用してよい。

1. 外部仕様との完全一致が必要な自明コード
   - 仕様を重複記載すると更新不整合を招く場合

例外を適用した場合は、PR説明または関連mdに理由を明記する。
